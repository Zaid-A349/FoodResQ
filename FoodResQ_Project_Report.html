1. Executive Overview & Problem Context

1.1 The Global & Local Food Dilemma

Globally, approximately 40% of all produced food is discarded while more than 828 million individuals experience chronic undernourishment. In urban Indian cities, this paradox is predominantly localized in banquet halls, marriage lawns, restaurant kitchens, corporate canteens, and sweet counters.

The Supply Bottleneck

Surplus Generation

Caterers and restaurants prepare excess safety buffers (15-25%). Once functions conclude, food is fresh and safe for 2–4 hours but discarded due to lack of immediate disposal logistics.

The Demand Bottleneck

Distribution Invisibility

Local shelters, student communities, and NGOs are unaware that fresh untouched food exists within a 1.5 km radius, resulting in waste rather than rescue.

1.2 Core Technological Solution

FoodResQ solves the connection friction through an intuitive, lightweight web platform engineered with three strict design tenets:

  • Sub-30-Second Posting: Food donors cannot navigate bureaucratic forms. FoodResQ provides one-tap auto-geolocation, pre-filled meal chips, and rapid posting.
  • Dignified Zero-Barrier Access: Hungry seekers and day-laborers can locate and claim nearby food without requiring invasive app downloads, complex KYC, or fee structures.
  • Verified NGO Bulk Channel: Structured pipeline for registered organizations (e.g., Robin Hood Army) with NGO Darpan IDs to claim and distribute bulk banquet volumes (100–500 portions) safely.

5. Frontend State Management & React Data Flow

5.1 React 18 Context API Architecture

FoodResQ avoids heavyweight third-party state managers (like Redux or MobX) in favor of React's native Context API (src/store.jsx). This minimizes bundle size (< 165 kB gzipped) while maintaining clean reactivity across the application tree.

┌─────────────────────────────────────────────────────────────────────────────┐ │ AppProvider (src/store.jsx) │ │ State: [user] [posts] [claimed] [history] [stats] [reviews] [isDbConnected]│ └──────────────────────────────────────┬──────────────────────────────────────┘ ┌───────────────────┼───────────────────┐ ▼ ▼ ▼ DonorDashboard.jsx NgoDashboard.jsx FindFood.jsx (Handover & Posts) (Bulk NGO Claims) (Live Map & Seeker)

5.2 Hybrid Persistence Strategy (Cloud + Local Cache)

To deliver a seamless offline-resilient user experience, store.jsx implements a dual synchronization strategy:

  • Initial Mount Handshake: Upon application boot, an asynchronous Promise.all requests live collections from /api/posts, /api/history, /api/reviews, and /api/stats.
  • Optimistic Updates: When a donor posts food or an NGO claims a batch, the state updates locally in memory immediately so the UI reacts in 0 milliseconds, while the background API call persists the change to MongoDB Atlas.
  • Local Storage Mirror: Key items (frm_user, frm_posts, frm_history) are mirrored to localStorage, allowing demo evaluation even when local dev servers are temporarily offline.

5.3 Auto-Expiration Engine

Surplus food is highly perishable. FoodResQ implements a proactive expiration watchdog inside store.jsx: 

// Evaluates active posts every 30 seconds
useEffect(() => {
  const t = setInterval(() => {
    setPosts((prev) => {
      const alive = prev.filter((p) => p.expiresAt > Date.now());
      return alive.length === prev.length ? prev : alive;
    });
  }, 30000);
  return () => clearInterval(t);
}, []);

Result: Listings disappear in real time once their timer hits zero, preventing seekers or volunteers from arriving at expired pickups.

6.2 Proximity Mathematics (Haversine Formula)

To sort available donations by proximity to the seeker, FoodResQ uses the mathematical Haversine Formula to compute great-circle distance between two GPS coordinates: 

function distKm(a, b) {
  const R = 6371; // Earth's mean radius in km
  const dLat = ((b.lat - a.lat) * Math.PI) / 180;
  const dLng = ((b.lng - a.lng) * Math.PI) / 180;
  const s = Math.sin(dLat / 2) ** 2 +
            Math.cos((a.lat * Math.PI) / 180) *
            Math.cos((b.lat * Math.PI) / 180) *
            Math.sin(dLng / 2) ** 2;
  return 2 * R * Math.asin(Math.sqrt(s));
}

8.1 The Complete Donor Workflow

  1. Step 1 (Surplus Incurred): Function ends or evening kitchen closes with 30–80 unconsumed portions.
  2. Step 2 (Rapid Post Creation): Donor logs in, taps Post Surplus Food, hits Detect My GPS (location coordinates and street name resolve automatically in 1 second), selects meal portions, and sets expiry (e.g., 60 mins).

  4. Step 4 (Incoming Seeker Alert): When a seeker or NGO taps "I'm Going", the donor's dashboard triggers an amber "🏃 Seeker En Route!" alert banner.
  5. Step 5 (Handover & Archive): Food is physically handed over. Donor clicks "✓ Mark Handed Over", archiving the item to MongoDB RescueHistory and refreshing active feeds.

12. Comprehensive Viva & Interview Preparation Guide (Part 1)

Q1: Why did you choose MongoDB Atlas over a traditional relational database (e.g. MySQL/PostgreSQL)?
Answer: Surplus food listings are semi-structured, transient documents with varying attributes (some have specific allergen notes, others have catering banquet trays, others have photos). MongoDB's flexible schema handles subdocuments like claimedBy arrays cleanly without complex SQL multi-table joins. Furthermore, MongoDB Atlas provides managed cloud scaling, automatic sharding, and high-availability replica sets ideal for geospatial operations.
Q2: Why is a dedicated Node.js/Express backend necessary instead of connecting React directly to MongoDB?
Answer: React executes client-side inside the user's browser. If React connected directly to MongoDB, the database connection string and cloud credentials would be publicly exposed in the browser's developer tools. Additionally, client browsers cannot maintain persistent TCP socket connections required by database drivers like Mongoose. The Express backend serves as a secure proxy enforcing authentication, input sanitization, and business logic.
Q3: How does your application prevent race conditions when multiple seekers claim the same meal simultaneously?
Answer: When a claim request is dispatched, the backend executes an atomic operation: FoodPost.findById(id) checking if status === 'available'. If already claimed, subsequent requests receive an HTTP 409 conflict. In high-concurrency production, Mongoose version keys (__v) and MongoDB atomic operators like findOneAndUpdate({ _id: id, status: 'available' }, { $set: { status: 'claimed' } }) prevent double-booking.
Q4: How does your reverse geocoding function work, and how do you handle rate-limits or network failure?
Answer: In src/utils/geo.js, when navigator.geolocation yields latitude and longitude, the app immediately writes the formatted coordinates (e.g., 28.98990, 77.68510) into the input box so the user has instant feedback. An asynchronous fetch with an AbortController timeout (4.5s) queries OpenStreetMap Nominatim. If Nominatim responds, the landmark/road/city name is prepended. If the request times out or is offline, it gracefully falls back to the exact GPS coordinates.
Q5: How does auto-expiration work without overloading the client or server?
Answer: In the database, every post stores a calculated expiresAt Date (createdAt + mins * 60000). On the backend, GET /api/posts queries { expiresAt: { $gt: new Date() } } so expired records are never transmitted. On the frontend, a 30-second interval filters the in-memory array, causing expired cards to vanish without requiring full page refreshes.

13. Comprehensive Viva & Interview Preparation Guide (Part 2)

Q6: What is the difference between Donor operations and NGO operations in FoodResQ?
Answer: Donors (restaurants, caterers, banquet owners) are suppliers who list surplus food in <30 seconds and confirm handovers. NGOs are bulk consumers and redistribution partners who possess vehicles and volunteer networks to collect 50–500 portions and redistribute them across multiple slum settlements or shelters. The application provides customized, role-aware dashboards for each.
Q7: How did you implement Symmetrical Form Architecture across Login, Donor Register, and NGO Register?
Answer: Previously, registration and login pages had different widths (448px vs 672px), disparate headers, and inconsistent styling. In the redesigned Auth.jsx, all three modes share an identical max-w-lg card container, identical rounded-3xl borders, and identical padding. A 3-way segmented pill switcher toggles between Sign In, Donor Register, and NGO Register without any layout shifting. NgoRegister.jsx directly renders <Auth initialTab="ngo" /> ensuring 100% architectural symmetry.
Q8: How does the application calculate physical distance between a seeker and food?
Answer: Using the Haversine formula in src/pages/FindFood.jsx. It converts latitude and longitude coordinates from degrees to radians and applies spherical trigonometry using Earth's radius (6,371 km). The UI renders this as intuitive proximity badges (e.g., "0.8 km away") and powers the "Nearest" sort filter.
Q9: What happens to a listing once a donor marks it as "Handed Over"?
Answer: The backend POST /api/posts/:id/complete endpoint removes the listing from the active foodposts collection and creates a permanent audit document in the rescuehistories collection. This updates the platform impact counter (Meals Rescued) and provides the donor and NGO with permanent records of their contribution.
Q10: What are the primary commands to run and build the application?
Answer:
  • npm run dev:all: Concurrently boots Express backend (port 5000) and Vite frontend (port 5173).
  • npm run server: Starts only the Node.js backend.
  • npm run dev: Starts only the Vite React frontend.
  • npm run build: Compiles optimized production bundle via Vite into dist/.
